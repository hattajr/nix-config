# Ticket contracts and slicing

Use the same behavioral contract as `triage`; read its [agent-brief guidance](../../triage/references/agent-brief.md) and [label policy](../../triage/references/labels.md). For a ticket published by this skill, use the attribution below instead of the triage disclaimer. Show it as part of the approved draft.

## GitHub ticket template

```markdown
> *This was generated by AI during ticket planning.*

## Parent
<Named source issue link; omit if the source is docs or a conversation.>

## Goal
<The complete, narrow outcome this slice delivers.>

## Current behavior
<Existing behavior, or what is absent in a fresh app.>

## Desired behavior
<Observable behavior, including material failure/edge cases.>

## Decisions and constraints
- <Settled interface, compatibility, migration, or product contract.>

## Acceptance criteria
- [ ] <Observable end-to-end behavior.>
- [ ] <Relevant failure/edge-case behavior.>

## Validation
<Public-interface checks or user flows proving the criteria.>

## Out of scope
- <Adjacent behavior not delivered by this ticket.>

## Blocked by
None (can start when otherwise eligible).
<!-- Or real named GitHub issue links, one per prerequisite. -->

## References
- <Durable design docs or decisions; omit if none.>
```

Optional concurrency notes may explain shared contracts/migration sequencing, but are advisory. Do not require exact implementation filenames, a checkout slug, a local plan file, or a private-function test strategy. Empty acceptance criteria or unresolved design questions mean not ready.

## Fresh-app example

Given approved account/dashboard design docs, prefer:
1. **Create and view an account:** persist an account through the supported interface, return it through a read path, show validation failures, and test those behaviors.
2. **Save a dashboard preference:** write/read a preference for an existing account with supported UI/API behavior; blocked by the account slice when that prerequisite truly gates it.
3. **Export a dashboard:** a complete export flow with error handling and tests; blocked by whatever dashboard behavior it actually needs.

Avoid:
1. Create every database table.
2. Build every API endpoint.
3. Add the whole UI.
4. Write tests at the end.

The first structure yields verifiable capabilities; the second produces broad horizontal layers that cannot be independently accepted. Bootstrap/foundation work can be a small verifiable slice when necessary, not a catch-all first ticket.

## Dependencies versus conflicts

- “Preferences need an account identity” can be a genuine blocking edge.
- “Both tickets might edit application wiring” is a concurrency warning, not automatically a blocker.
- “Part of #42” means hierarchy, not that #42 must close before the child can start.
- `ready-for-agent` means specified/approved; it does not mean dependencies are already integrated.

`implement-issues` checks the live base branch and claims again before starting. It does not automatically implement a targeted issue's parent, children, or blockers.

## Parent tracking

When splitting an existing executable issue, propose a minimal parent update for approval, such as a `Tracking only` note and named child task list, with removal of its execution-readiness label. Preserve original context and non-goals; do not replace its intent with a second copy of every child brief. Parent and child links provide navigation, not another authoritative specification.

Do not automatically close the parent or mark child task boxes complete at publication. If parent edits are not approved, resolve the duplicate-executable-scope problem before publishing children as ready.

## Partial publication

The final summary must distinguish proposed tickets, created issues, verified dependency links, and ready labels. If tickets exist but relationship/state writes failed, identify those URLs and missing operations. Never duplicate already-created tickets simply because the batch did not finish. Keep all persisted recovery details on GitHub or in the user-facing report when GitHub cannot accept writes.
